How it was captured

The source ships no HTML

rajasthansubsidy.com is a client-rendered Vite + React single-page app: the server returns an empty <div id="root"> and a 1.88 MB JavaScript bundle. Fetching the URLs directly yields nothing but a shell, and there is no sourcemap — /assets/index-*.js.map returns the SPA's own index.html fallback rather than a map.

So the pages were rendered in headless Chrome with a 20-second virtual time budget and the resulting DOM converted to structured text. The route list came from the bundle's router table, which turned out to declare seven more routes than sitemap.xml does — the four legal pages plus the admin area.

Findings

What the capture told us

The source already runs a backend. Firebase Auth and Firestore drive the blog, the blog posts and the Work Showcase records table, all administered through /admin. All three render empty in production today — the showcase table literally reads "Records will appear once added by Admin." That is the clearest possible signal about which collections need a CMS on day one, and which are fine as code.

Nothing is server-rendered. Every page ships the same empty shell and hydrates client-side; titles are patched in after hydration, leaving two <title> tags in the DOM. For a site whose entire audience arrives by searching for a scheme name, that is the single largest thing to fix — which is why the rebuild prerenders everything.

1.88 MB of JavaScript on first load, including jsPDF, a PDF viewer and a Google API client, shipped to every visitor. And the four legal pages are linked from the footer but missing from sitemap.xml.

Reuse boundaries

Three buckets, enforced in the data

Not all scraped content can simply be rebranded. The split below is not advisory — it is how content/data/ is actually organised.

Reused in full

Public policy fact

Scheme names, subsidy percentages, eligibility criteria, guideline PDFs.

  • Sourced from government publications
  • Verified against the linked PDFs
  • Lives in schemes.ts
Rewritten

Generic category copy

Service names, section headings, structural framing.

  • Structure retained, wording ours
  • No distinctive phrasing carried over
  • Lives in services.ts, home.ts
Not copied

Another firm's identity

Team, contact details, "700+ units served", "₹50+ Cr secured", the 4.9 rating, named client outcomes.

  • Fields exist, values are TODO(brand)
  • 25 placeholders await real figures
  • Client names also carry a consent duty
Why this matters

Those statistics are factual assertions about a specific firm's track record, and the success stories name real businesses alongside real disbursement amounts. Republishing them under Dakshyam Consulting would misrepresent the business and reuse those clients as references without their consent. Every one of those fields is modelled and waiting — it just needs Dakshyam's own verifiable numbers.

Architecture

Pages render. They never own content.

Every string, figure, image reference and document link comes from one place. No page imports from content/data/, and no copy is hard-coded in JSX. Three layers, each with exactly one job:

Presentation app/**/page.tsx

Layout and markup only. Reads from the repository, knows nothing about where content lives.

imports
Access lib/content/repository.ts

The only public API. Each function declares a use cache scope with an invalidation tag and a freshness budget.

delegates to
Source lib/content/providers/ Migration point

static-provider.ts reads typed TypeScript today. An api-provider.ts will read a CMS tomorrow. Both satisfy the same ContentProvider interface.

The key decision

Async from day one

Every provider method returns a Promise — even reading a local array.

That looks like overhead while the data sits in memory. It is the thing that makes the migration cheap. If the static layer were synchronous, introducing a backend would turn every call site async — a refactor touching every page, landing in the same change that introduces network failures and loading states. Keeping the signature async now means the cutover really is a one-line change.

Migration — a real sequence

Adding the backend, in order

  1. Pick the source

    A git-based CMS (Keystatic, TinaCMS) keeps the static provider and just gives editors a UI — cheapest if the only pain is "an editor can't change copy". A headless CMS (Sanity, Payload) earns its keep once blog and success stories are actively maintained. A real database is needed only when content turns transactional: application tracking, client logins, document uploads.

  2. Model the schema from the types

    lib/content/types.ts already is the schema — collections, field types, the relation from a success story to its scheme, and the published / displayOrder editorial flags.

  3. Write api-provider.ts

    Implement ContentProvider against the new source, validating responses at the boundary with Zod so a bad payload fails loudly in one place instead of rendering undefined into a live page.

  4. Flip one line

    providers/index.ts selects the provider from an environment variable. Both sources can run side by side during cutover, and rollback is instant.

  5. Wire invalidation

    A webhook route maps the changed collection to its tag and calls revalidateTag. The tags already exist — the CMS just has to name one.

  6. Seed the data

    Because the data is typed and the interface is shared, the migration script imports the static provider and writes straight into the CMS. Collections can move one at a time — blog to the CMS while schemes stay in code, where a policy change gets code review.

The point

No page changes in any of those six steps.
